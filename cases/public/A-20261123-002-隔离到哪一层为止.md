# A-20261123-002 · 多租户隔离：隔离到哪一层为止

- 状态：`verified`（自有决策档案 ADR，已脱敏；原档自带脱敏自检）
- 核对日期：2026-11-23

## 背景与约束

- 场景（抽象）：为一个多租户平台定隔离方案，需要在合规强度与运维成本之间取舍。
- 约束：客户对数据隔离有可被写进合同的明确要求；平台需要可持续地增加租户。
- 决策时掌握的信息：不同隔离层级在正常运行下表现无异，区别只在"出事后如何解释"。

## 决策链

- **候选**（按隔离强度递增）：应用层共享库做逻辑过滤 / 共享库+独立 schema / 每租户独立库。
- **选择**：每租户独立库（物理隔离）。
- **决定性理由**：**合规的可解释性**——"我们代码里做了过滤"不是客户要的答案，客户要的是一句能写进合同的话。
- **代价**：运维复杂度上升（迁移/监控/备份都要乘以租户数）、加租户不再是零成本、跨租户统计需要额外聚合层。
- **配套设计**：租户上下文在平台层强制注入（业务代码拿不到不带租户的连接）；迁移由平台统一编排保证版本一致；职责分层，隔离只影响平台层、上层对它无感。

## 机制层沉淀

- **决策标准**：技术强度差异在正常情况下不会被考验，真正的判据是"出事后的可解释性 + 客户敢不敢签"。
- **授权边界**：隔离约束下沉到平台层强制，而不是靠每个业务代码自觉——把"必须遵守"变成"想违反都拿不到连接"。
- **取舍意识**：选强隔离就是主动承担运维乘数，不能既要合规可解释又要零成本加租户。

## 适用边界

- **适用**：客户对数据隔离有合同级要求、且合规解释权重高于运维成本的场景。
- **不适用**：内部工具、无合规约束、租户数量极少且稳定的场景——物理隔离的运维乘数不划算。
