# xingtu-agent · Agent 落地案例集

> 本地构建中 · 尚未推送公开。本仓记录「Agent 在真实任务里怎么落地」的案例与取舍，不是 Agent 框架源码。

[![License: MIT](https://img.shields.io/badge/License-MIT-orange.svg)](./LICENSE) ![状态](https://img.shields.io/badge/状态-本地构建-lightgrey)

## 一句话定位

收集 Agent 落地的真实场景：任务怎么拆、授权边界怎么定、记忆/回执怎么留、失败怎么恢复——只沉淀决策层次与适用边界，不复述「Agent 是什么」。

## 为什么单独建这个仓

Agent 的文章很多，能说清「当时为什么这么选、后来遇到什么、边界在哪」的很少。本仓的价值不是功能清单，是**决策链**：一个 Agent 方案在什么约束下成立、换一个场景为什么不成立。

## 与相邻仓的边界

| 仓 | 管什么 | 不管什么 |
|---|---|---|
| `xingtu-super-agent` | 跨 Agent 协作系统（XSA）的方法论与最小实现 | 不收录第三方 Agent 案例 |
| `xingtu-agent-skills` | 可安装复用的 Agent 技能 | 不做场景决策复盘 |
| **xingtu-agent**（本仓） | Agent 落地场景的案例与决策取舍 | 不做技能库、不做框架源码 |

## 核心内容

- **场景案例卡**：统一模板记录背景约束、方案选择、验证结果、适用边界。
- **决策链**：为什么选 A 不选 B，当时的判断依据，事后是否成立。
- **失败档案**：Agent 跑偏、授权越界、回执缺失的真实模式与护栏做法。

## 关于知识问答助手类案例

团队知识问答助手（含 spec 驱动的需求→设计→任务→验收链路）属于**方法论层可复用案例**：本仓只收录脱敏后的机制与决策链（如何拆 spec、如何做验收、如何留证据），不收录具体项目实体、代码、内网路径或客户信息。相关占位见 [`cases/_pending/`](cases/_pending/)，补齐脱敏稿前不得入库。

## 快速开始

```bash
git clone <仓库地址> xingtu-agent
cd xingtu-agent
# 案例模板 cases/_TEMPLATE.md
```

新增案例先读 [`cases/_TEMPLATE.md`](cases/_TEMPLATE.md)。每条必须带**状态标注**与**证据来源**；没有证据的推断标 `design`，本机实测留痕的才标 `verified`。

## 案例状态标注（全仓统一）

| 状态 | 含义 |
|---|---|
| `design` | 仅设计/设想，未验证 |
| `public-source` | 公开资料整理，非本仓实测，带链接与核对日期 |
| `verified` | 本机实测，有可核对证据 |
| `production` | 生产环境在用 |

## 入库规范

- 实体脱敏是硬门槛：客户名、人名、内网域名、内部平台链路、具体业务数据一律不入库。
- 案例保留决策层次与时间线，脱敏后不失现场感；只出机制，不出实体。
- 数字标注来源与验证程度；二手数据不作为判据。
